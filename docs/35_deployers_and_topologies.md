# Deployers and Topologies

## Supported Topologies

The framework uses these canonical names:

```text
local
vm-single
vm-distributed
```

The menu shows friendlier aliases:

```text
local  local machine
vm1    one virtual machine
vm3    three virtual machines
```

## Current Behavior

`local` is the default topology for development and validation on the
operator's machine.

`vm-single` deploys the environment on one VM with framework-managed
Kubernetes. It's useful to validate a complete installation without
splitting services across machines.

`vm-distributed` separates infrastructure roles: common services, connectors,
components, and, when applicable, observability. The topology is configured
through local overlays or profiles ignored by Git. Before running levels, the
framework must validate SSH, kubeconfig, HTTP, and Ingress with preflights.

The three topologies must share functional namespaces, adapter contracts, and
per-topology URL resolution. This rule prevents one topology from being
contaminated with domains, credentials, or artifacts generated by another.

## Closure Scope by Adapter and Topology

The following matrix separates implemented support from official closure
evidence:

| Adapter | `local` | `vm-single` | `vm-distributed` |
| --- | --- | --- | --- |
| `inesdata` | Implemented and used as the local development/validation path | Implemented and validated as the reference VM environment | Implemented and validated as the reference distributed environment |
| `edc` | Implemented; validated before the recent topology reconciliation and pending revalidation for current evidence | Implemented; pending official validation after the recent reconciliation | Implemented and officially tested as the closure path |

For auditable `edc` evidence, use `vm-distributed`. The other EDC paths are
kept as framework capabilities and must be revalidated before being presented
as closure results.

## Naming Convention

For environment variables exported by the user, the framework's public
convention is `PIONERA_*`.

Examples:

```text
PIONERA_VM_EXTERNAL_IP
PIONERA_VM_COMMON_IP
PIONERA_VM_PROVIDER_IP
PIONERA_VM_CONSUMER_IP
PIONERA_INGRESS_EXTERNAL_IP
```

In contrast, `deployer.config` keeps internal keys without a prefix, for
example `VM_EXTERNAL_IP` or `INGRESS_EXTERNAL_IP`. This doesn't mean the user
should export those legacy variables: the loader automatically converts the
`PIONERA_*` overrides to the internal configuration keys.

### Public Names and SQL Resources

Public dataspace names, namespaces, hostnames, and Keycloak realms must stay
lowercase. The framework accepts hyphens where the resource allows them; for
example, `pionera-edc` is a valid name for an EDC dataspace and its Keycloak
realm.

SQL resources derived from the dataspace don't use hyphens. The framework
internally normalizes `-` to `_` when generating PostgreSQL database and role
names. For example, the `pionera-edc` dataspace generates:

```text
pionera_edc_rs
pionera_edc_rsusr
pionera_edc_wp
pionera_edc_wpusr
```

These SQL names must be derived from `DS_1_NAME`. They must not be edited by
hand in the generated deployment artifacts.

## Configuration Layers

The shared infrastructure configuration is now resolved in layers:

```text
deployers/infrastructure/deployer.config
deployers/infrastructure/topologies/local.config
deployers/infrastructure/topologies/vm-single.config
deployers/infrastructure/topologies/vm-distributed.config
```

Rule of thumb:

- `deployers/infrastructure/deployer.config` must contain the common, stable
  base
- `deployers/infrastructure/topologies/*.config` must contain only overrides
  that depend on the active topology
- `PIONERA_*` variables still have the highest priority

The bootstrap automatically creates the local `.config` files from their
`.config.example` files when they don't exist yet, and doesn't overwrite
local files that have already been adjusted. The `.config.example` files are
the versionable templates; the local `.config` files must not be pushed to
the repository.

During the migration, the framework still tolerates topology keys in the
common base so existing environments don't break. Even so, the CLI already
emits warnings when it detects that drift and points you to the right
overlay, for example `deployers/infrastructure/topologies/local.config` or
`deployers/infrastructure/topologies/vm-single.config`.

The adapters' `deployer.config` files (`inesdata`, `edc`) remain independent
of this layer and keep the identity of the dataspace, connectors, components,
and each adapter's own flags.

## Canonical Namespaces

The current state of the framework uses the `role-aligned` profile for
INESData. All topologies must resolve the same namespace roles:

```ini
COMMON_SERVICES_NAMESPACE=common-srvs
DS_1_NAME=pionera
DS_1_NAMESPACE=core-control
NAMESPACE_PROFILE=role-aligned
DS_1_REGISTRATION_NAMESPACE=core-control
DS_1_PROVIDER_NAMESPACE=provider
DS_1_CONSUMER_NAMESPACE=consumer
COMPONENTS_NAMESPACE=components
```

| Namespace | Role |
| --- | --- |
| `common-srvs` | Common services: Keycloak, MinIO, PostgreSQL, and Vault |
| `core-control` | Registration-service and dataspace control plane |
| `provider` | Connector group/placement used by the base validation flows |
| `consumer` | Connector group/placement used by the base validation flows |
| `components` | Optional components: Ontology Hub, AI Model Hub, and Semantic Virtualization |
| `ingress-nginx` | Cluster ingress controller |
| `kube-system` | Kubernetes infrastructure |

The names `provider` and `consumer` are conventions of the validation
environment, not rigid functional roles. A connector acts as provider or
consumer depending on the test flow. For more than two connectors, define the
inventory in `DS_1_CONNECTORS` and, if you need to control their placement,
use `DS_1_CONNECTOR_NAMESPACES`:

```ini
DS_1_CONNECTORS=org2,org3,partnera
DS_1_CONNECTOR_NAMESPACES=org2:provider,org3:consumer,partnera:provider
DS_1_VALIDATION_PAIRS=org2>org3,partnera>org2
LEVEL4_CONNECTOR_RECONCILIATION_MODE=full
```

In the `deployer.config.example` files, these keys are intentionally empty to
keep the current deployment:

```ini
DS_1_CONNECTOR_NAMESPACES=
DS_1_VALIDATION_PAIRS=
```

With those empty values, the framework uses the historical convention: the
first connector in `DS_1_CONNECTORS` is associated with the `provider` group,
the second with the `consumer` group, and additional connectors with the
dataspace namespace. You only need to fill in these variables when you want
to explicitly control each connector's placement or run validation pairs
other than the base pair.

`DS_1_CONNECTOR_NAMESPACES` decides where each connector is deployed.
`DS_1_VALIDATION_PAIRS` decides which pairs are used as source/destination in
the automated validations. `LEVEL4_CONNECTOR_RECONCILIATION_MODE=full` keeps
the historical level 4 behavior: it reconciles the configured set and
recreates existing connectors to leave a clean deployment. To add connectors
without recreating the ones that are already healthy, use
`LEVEL4_CONNECTOR_RECONCILIATION_MODE=additive`.

In `additive` mode, the framework preserves the access users and credentials
of the existing connectors. By default, it also reconciles the technical
Keycloak client associated with each preserved connector through
`LEVEL4_SYNC_EXISTING_CONNECTOR_KEYCLOAK_CLIENTS=true`; this reconciliation
syncs roles, groups, and the public certificate used by OAuth/DSP, but it
doesn't regenerate the `user-conn-*` users or their passwords.

If the mapping keys are not defined, the framework keeps the historical
behavior: first connector as validation source, second as validation
destination, and additional connectors in the dataspace namespace.

For Semantic Virtualization, level 5 syncs the sources needed for the
component's validation: `morph-kgv`, `mapping-editor`, and `Automap`.
`morph-kgv` is packaged as the runtime API, `mapping-editor` is deployed when
the UI/editor is enabled, and `Automap` is available as a mapping generation
tool for traceability, readiness, and a deterministic level 6 baseline. That
baseline doesn't invoke an LLM or read secrets: it uses versioned fixtures to
check schema/ontology extraction, reuse of an ontology governed by Ontology
Hub, controlled RDF materialization, and evaluation metrics.

The `morph-kgv` validation also checks that the synced source exposes the
component's current contract: versionable installation, `run_query.py`,
`morph-kgv serve config.ini`, the `config.ini` examples, and the `/sparql`
endpoint.

The central resolution lives in:

```text
deployers/shared/lib/namespaces.py
deployers/inesdata/deployer.config.example
```

The distributed topology must change placement, addresses, and routing, but
it must not change these functional names unless an explicit, compatible
migration is introduced in the common namespace resolver.

## TLS on VM Topologies

On `vm-single` and `vm-distributed`, the framework enables by default an
Ingress TLS reconciliation for the environment's public hostnames. The same
operation prepares, when needed, the `common-tls-cacerts` truststore that the
connectors mount to trust both the Ingress's internal CA and the public CAs
included in Java's base `cacerts`.

This behavior is shared by the adapters and prevents the use of real HTTPS on
internal or public paths from breaking DSP calls between connectors. If the
reconciliation is disabled, the operator must manually ensure that the
Ingress certificates and the connectors' truststores are consistent.

## Cold Start and Readiness

On a clean installation or after restarting the environment, some services
need more time to become operational even though their Kubernetes resources
already exist. This applies especially to `local` and `vm-single`, where local
images, persistent volumes, internal DNS, Vault, Keycloak, databases,
connectors, and components are initialized on the same machine.

If a level fails because of a readiness timeout, check the logs of the
component and of the service it depends on before relaunching the affected
level. A re-run completes successfully when the first attempt left persistent
resources or local images initialized. This behavior must not hide recurring
failures: if the error reproduces after a restart or from a clean
environment, it must be treated as an issue of the framework, the deployment,
or the corresponding component.

## Local

`local` uses Minikube.

Typical flow:

```bash
python3 main.py menu
python3 main.py inesdata hosts --topology local --dry-run
python3 main.py edc hosts --topology local --dry-run
```

`hosts` entries usually resolve to `127.0.0.1` and rely on `minikube tunnel`
to expose the Ingress on the `local` topology.

If a specific environment needs an address other than loopback, declare it
explicitly in:

```text
LOCAL_HOSTS_ADDRESS
LOCAL_INGRESS_EXTERNAL_IP
```

These keys must live in:

```text
deployers/infrastructure/topologies/local.config
```

If those keys are empty, the framework keeps the canonical loopback mode.

### Local Sizing

For a local machine with Docker Desktop and a full validation stack, also
declare the Minikube resources in the local overlay:

```text
LOCAL_RESOURCE_PROFILE=coexistence
MINIKUBE_DRIVER=docker
MINIKUBE_CPUS=10
MINIKUBE_MEMORY=18432
MINIKUBE_PROFILE=minikube
```

This recommendation doesn't come from a generic rule, but from the
degradation observed during `Level 6` locally:

- Docker Desktop showed `20 CPUs available` and `14.9 GB` available to the
  engine.
- The `minikube` container had a real cgroup limit of `12884901888` bytes,
  that is `12 GiB`.
- Kubernetes saw the node with `20 CPU` and `15996068Ki` of memory, about
  `15.25 GiB`.
- Therefore, the Kubernetes scheduler could reason about more memory than
  Docker actually allowed the container.
- The Minikube cgroup recorded `oom_kill=3` and the Kubernetes events
  recorded `SystemOOM`, `NodeNotReady`, and restarts of Keycloak, Ontology
  Hub, Elasticsearch, AI Model Hub, connectors, and `storage-provisioner`.
- The local run already contained common services, an INESData dataspace,
  components, Kafka, and the Newman, Kafka, and Playwright validation suites.
- Many application pods were in QoS `BestEffort`, without requests or
  limits, so Kubernetes couldn't reliably reserve memory or protect them
  under memory pressure.

The estimate is computed as follows:

- stable consumption observed after recovery: about `5.1 GiB` in the
  Minikube container;
- observed cgroup peak: about `9.3 GiB`, but already with OOM, so the real
  peak needed was above the available headroom;
- current effective limit: `12 GiB`, insufficient because it produced
  `SystemOOM` and `NodeNotReady`;
- minimum additional headroom for the control plane, probes, Kafka, the
  Playwright browser, JVMs, and caches: `3-4 GiB`;
- additional headroom if `inesdata` and `edc` stay installed on the same
  local topology, with two dataspaces and their connectors: `2-4 GiB`;
- resulting stable range for the full local cluster: `16-18 GiB`;
- recommended point if the host allows it: `18 GiB` for Minikube and
  `10 CPU`.

Rules of thumb:

- don't set `MINIKUBE_MEMORY` above the memory Docker Desktop can allocate to
  the engine;
- leave at least `4-6 GiB` outside Minikube for WSL, Docker Desktop, VS Code,
  the browser, and the tests' Python/Node process;
- if Docker Desktop stays around `14.9 GB`, the full local mode with
  `inesdata`, `edc`, components, and `Level 6` is not reproducible in a
  stable way; in that case use one adapter at a time or run the full
  validation on `vm-single`;
- `8 CPU / 12288 MB` remains a minimum profile for development or smoke
  tests, not a stable baseline for a full `Level 6` with both adapters;
- `10 CPU / 16384 MB` is the reasonable minimum for a more demanding local
  validation if Docker Desktop has at least `20 GB`;
- `10 CPU / 18432 MB` is the recommended baseline when you intend to validate
  the coexistence of `inesdata` and `edc` locally;
- `Level 1` queries the real memory exposed by Docker Desktop and warns if
  the environment ends up in a single-adapter profile;
- `Level 3/4/5` block the installation or extension of the second local
  adapter when another adapter is already active and the effective capacity
  is below the coexistence baseline; in interactive mode they offer a
  controlled adapter switch that deletes only the managed namespaces and
  runtime artifacts of the previous adapter, preserving `common-srvs`, and
  requires exact confirmation before running the cleanup;
- in non-interactive runs, the local adapter switch is considered
  destructive and requires `PIONERA_LOCAL_ADAPTER_SWITCH_CONFIRM` with the
  value `SWITCH TO EDC` or `SWITCH TO INESDATA`;
- `Level 6` in stable mode evaluates the local capacity before running the
  suites; if it detects `inesdata` and `edc` coexisting with less than
  `18432 MB` effective, it blocks the validation to avoid results contaminated
  by `NodeNotReady`;
- `401`, `500`, or functional application crashes should not be interpreted
  as a CPU problem by default, but they must be considered contaminated if
  the `Level 6` postflight records OOM, `NodeNotReady`, or new restarts.

If you change `MINIKUBE_CPUS` or `MINIKUBE_MEMORY`, you have to recreate the
cluster from `Level 1`, because Minikube doesn't reliably resize a profile
already created by the framework. Before doing so, first raise Docker
Desktop's resource limit so the new Minikube value is actually supported.

For reproducibility, `Level 6` on the `local` topology resolves
`--validation-mode auto` as `stable`. This mode keeps the same suites and
assertions, but reduces the overlap between Newman, Kafka, Playwright, and
components. If you need to prioritize speed locally, use
`--validation-mode fast` or `PIONERA_VALIDATION_MODE=fast`.

As part of that stable mode, `Level 6` checks the health of the local runtime
with `kubectl` before launching the suites and takes another sample at the
end. The `local_stability_preflight.json` and
`local_stability_postflight.json` artifacts help separate application
failures from pod restarts or `NodeNotReady` events.

The reference local diagram is available in [Getting started](./32_getting_started.md#local-view).

## VM Single

`vm-single` represents a virtual machine backed by Kubernetes. To make the
quickstart reproducible, `Level 1` by default prepares the framework-managed
k3s cluster inside the VM and then runs the access, ingress, storage, and
permission checks.

Current state of the framework:

- `inesdata`: `Level 1` to `Level 6` operational, with a shared `Level 5` for the configured components
- `edc`: path implemented, pending official validation after the recent topology reconciliation

The topology needs an external address, supplied through one of these variables:

```text
PIONERA_VM_EXTERNAL_IP
PIONERA_VM_SINGLE_IP
PIONERA_VM_SINGLE_ADDRESS
PIONERA_HOSTS_ADDRESS
PIONERA_INGRESS_EXTERNAL_IP
PIONERA_MINIKUBE_DRIVER
PIONERA_MINIKUBE_CPUS
PIONERA_MINIKUBE_MEMORY
PIONERA_MINIKUBE_PROFILE
```

Example:

```bash
PIONERA_VM_EXTERNAL_IP=192.0.2.10 \
python3 main.py inesdata hosts --topology vm-single --dry-run
```

How to get the right IP:

```bash
hostname -I
kubectl get ingress -A
```

Rule of thumb:

- use the IP from `hostname -I` as a starting point if you run the framework
  directly on the VM;
- set as the final value the public IP/DNS that ends at the VM or at the
  external proxy that publishes the Ingress;
- after `Level 1`, if the public proxy or the VM IP don't match the active
  configuration, update the `PIONERA_VM_EXTERNAL_IP` environment override or
  the `VM_EXTERNAL_IP` key inside
  `deployers/infrastructure/topologies/vm-single.config` before `Levels 3-6`.

The persisted `vm-single` keys must live in:

```text
deployers/infrastructure/topologies/vm-single.config
```

## VM Distributed

`vm-distributed` represents a distributed validation topology. The current
configuration model lets you prepare either a single logical Kubernetes
cluster with several nodes/VMs or a multi-cluster evolution based on
per-role kubeconfigs. The base interpretation is still:

```text
common    common services
provider  provider connector
consumer  consumer connector
```

The expected node labels are:

```text
pionera.role=common
pionera.role=provider
pionera.role=consumer
```

This validates physical placement by role and communication between nodes
while keeping a single Kubernetes control plane. In deployments with
external infrastructure, where connectors live on different VMs or servers,
the menu assistant also collects per-role kubeconfigs (`common`, `provider`,
`consumer`) so the operational implementation of `vm-distributed` can evolve
without reopening the configuration model.

The current real execution of `vm-distributed` is enabled both for a
distributed logical Kubernetes cluster and for separate per-role k3s
clusters. `K3S_KUBECONFIG_COMMON` operates the common services and the
dataspace control plane. In level 4, `K3S_KUBECONFIG_PROVIDER` is used for
Helm, ConfigMaps, rollouts, logs, and port-forward of provider connectors,
and `K3S_KUBECONFIG_CONSUMER` is used for the same operations on consumer
connectors. Level 5 uses `K3S_KUBECONFIG_COMPONENTS` when components target a
specific context.

In multi-cluster mode, the connectors still need to reach the common services
at runtime: Keycloak, Vault, MinIO, PostgreSQL, and Registration Service must
be exposed through DNS, ingress, proxy, or valid routes from the provider and
consumer clusters.

For this shared mode to match the upstream (PIONERA) reference diagram, the logical cluster must
include Kubernetes nodes for the connector VMs. If the kubeconfig only shows
the common node, the `provider` and `consumer` namespaces will be created
logically, but their pods will keep running on the common VM. On
`vm-distributed`, the connector charts accept `nodeSelector` and the adapter
derives it from `VM_PROVIDER_K8S_NODE` and `VM_CONSUMER_K8S_NODE`; for
example, `org2` is pinned to `pionera20` and `org3` to `pionera3` when those
VMs are already part of the k3s cluster.

### The `vm-distributed` Assistant

In the interactive menu, the `W - vm-distributed assistant` option is the
entry point to prepare and review the distributed topology. If invoked from
another topology, it keeps compatibility with the previous shortcut and opens
the configuration wizard directly after confirming the switch to
`vm-distributed`. When `vm-distributed` is already active, the assistant lets
you:

- prepare the local infrastructure, topology, and adapter `.config` files;
- automatically derive `KC_URL`, `KC_INTERNAL_URL`, `KEYCLOAK_*`, and
  `MINIO_*` from `DOMAIN_BASE` when those values are empty or still generated
  defaults, keeping any custom value;
- show the VM plan per role (`common-services`, `provider-connectors`,
  `consumer-connectors`);
- run the static preflight of domains, addresses, kubeconfigs, connectors,
  reconciliation, SSH, deployment mode, and hosts;
- preview the deployment and hosts plan without modifying the environment;
- run, after confirmation, non-destructive SSH/HTTP checks.

The local files it prepares are:

```text
deployers/infrastructure/deployer.config
deployers/infrastructure/topologies/vm-distributed.config
deployers/<adapter>/deployer.config
```

The assistant asks for domains, VM IPs/DNS, an optional SSH user for remote
NGINX synchronization, preflight SSH metadata, k3s kubeconfigs, connectors,
connector placement, and validation pairs. If you don't know a value, type
`?` in the field to see what it means, how to choose it, and which Ubuntu
commands help discover it. For the connector inventory, the assistant
proposes an initial placement alternating the `provider` and `consumer`
groups; edit that value before saving if your deployment uses a different
distribution. The assistant only writes local `.config` files ignored by Git
and doesn't run deployments by itself.

The versioned configuration uses placeholders. Real host, IP, user,
kubeconfig, remote workspace path, or specific domain values must live only
in local `.config` files ignored by Git or in environment variables.

The remote preflight uses `ssh` with `BatchMode=yes`, a configurable timeout,
and read commands such as `hostname`, `id`, `/etc/os-release`, container
runtime detection, `kubectl`/`k3s`, listening ports, and local `curl`. It
doesn't install packages, change the firewall, modify certificates, or deploy
resources.

If the checklist marks `ready` with the detail `multi-kubeconfig connector
deployment enabled`, the configuration describes a real multi-cluster
deployment: before running level 4, check that each kubeconfig reaches its
cluster and that the common services are resolvable from provider and
consumer.

On `vm-distributed`, levels 2, 3, and 4 idempotently refresh the NGINX
routing configuration when `VM_COMMON_IP` and `DS_DOMAIN_BASE` are defined.
The framework generates HTTP routing for the dataspace, the registration
service, and the configured connectors, plus a `stream` proxy for common
services. If `VM_SSH_USER` is defined, it also syncs NGINX on the remote
connector VMs; if it isn't, it skips that part with a warning and doesn't
abort the level.

For deployments with external connectors or distributed infrastructure, read
[External connector readiness](./45_external_connector_readiness.md) (ES)
before running deployment levels.

### Operational Alignment

To operate `vm-distributed`, the configuration must keep the framework's
common contract:

- use the canonical namespaces described in this document;
- keep `NAMESPACE_PROFILE=role-aligned`;
- resolve `common-srvs`, `core-control`, `provider`, `consumer`, and
  `components` through `deployers/shared/lib/namespaces.py`;
- move workloads between nodes with labels, `nodeSelector`, affinity, or
  tolerations, not with alternative namespace names;
- keep the Newman collections, the Kafka validation, and Playwright consuming
  the same adapter variables as `local` and `vm-single`;
- store the topology's own overrides in
  `deployers/infrastructure/topologies/vm-distributed.config`;
- use public `PIONERA_*` variables for user overrides.

Minimum checklist before declaring a distributed run valid:

1. `python3 main.py inesdata hosts --topology vm-distributed --dry-run`
   generates consistent entries.
2. The deployment plan shows the same namespace roles as `local` and
   `vm-single`.
3. `Level 1` validates Kubernetes access, ingress, storage, and permissions.
4. `Level 2` deploys `common-srvs`.
5. `Level 3` deploys `core-control`.
6. `Level 4` deploys connectors in `provider` and `consumer`.
7. `Level 5` deploys components in `components` when they are configured.
8. `Level 6` runs Newman, Kafka, Playwright, and component validations
   without special hardcoded paths for `vm-distributed`.

## Interpreting the VM3 Diagram

The `vm3` diagram must be read as a conceptual view.

![PIONERA distributed validation environment](<./pionera_distributed_validation_environment.png>)

In the first implementation, `vm3` means a single Kubernetes or k3s cluster with three VM-backed nodes. Namespaces belong to the cluster. Workloads are scheduled on the expected VM/node using labels, `nodeSelector`, or affinity.

The EDC Management API is considered internal or operation-oriented. Public interactions between participants must happen through the connector's protocol, catalog, negotiation, and transfer endpoints.

## Routing

The default routing model is host-based:

```text
keycloak.<domain>
minio.<domain>
registration-service-<dataspace>.<ds-domain>
conn-<connector>-<dataspace>.<ds-domain>
```

Path-based routing remains a planned extension for when a single public
domain becomes a strict requirement.
